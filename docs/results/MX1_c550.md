## 3. Completion and deviations

S, P, B, D (the required core) complete. T complete, 5/5 TaskBody tests pass.
C and V complete for Qwen3-0.6B, the spec's required minimum, and re-verified
under MX-2's layout (§6). E: 18 of 19 cells re-measured, 39 of 40 plans solved
(§7). Paged executor deferred, as §5 allows.

Deviations, all **verified** unless noted:

1. **Last-arriver handoff off** (`--nonpaged-la 0`, both phases), as the
   validating MX-C/MX-T cells ran. A prefill plan carrying it is refused at
   load (`ServingRuntime.cuh` needs `TILEMEGA_SERVING_SEQ==1`); on decode it
   hit §9.1.
2. **Fragment-packed weights, GEMV excluded** (MX-2). MX-1 measured every cell
   row-major: the harness passed `--nonpaged-weight-layout row` and
   `cli.py` pinned non-paged plans to row regardless of the feature. Both are
   fixed and the harness is now in git (`scripts/mx_serving_cell.sh`), so the
   switch is reproducible from the repository. All 39 solved plans are tiled
   with no GEMV variant; §7 carries the A/B that justifies each choice.
3. **torch.compile MoE experts run eager.** This MetaX torch has no
   `torch._grouped_mm`; the harness probes for it, falls back, and records
   `grouped_mm_error` in the measurement (commit `217024176`).
4. **Baselines: one round for the MoE cell, two for the dense cells** — the
   three-round protocol was reduced to one on request, rounds 1–2 being done.
5. `counted_dependency_cg` fails (`counted_dependency_cg_test.cpp:105`).
   **Inferred pre-existing**: it and `BuildDependencyTableLinear` last changed
   before the baseline and nothing here touches the host-side lowering it
   asserts on; confirming needs a build at `243fe9d06`.

## 7. Performance

Protocol: ISL/OSL 64/1024, B ∈ {1,2,4,8,16}, random weights, median over
rounds, one job per card under `gpu_guard`. TTFT from N=1, E2E from N=OSL,
TPOT=(E2E−TTFT)/(OSL−1), throughput=B·OSL/E2E, MBU=(weights+KV)/(TPOT·1.64
TB/s) — same formula in TileMega and the baselines (`measure.py:139`,
`baseline_common.py:103`, `vllm_baseline.py:101`), so the ratios are
like-for-like (**verified**).

Every round is in [`MX1_serving_c550.csv`](MX1_serving_c550.csv), the per-cell
decomposition in [`MX1_gap_c550.csv`](MX1_gap_c550.csv). Decode runs mode L1
with `--decode-loop auto`, the only non-paged mode whose plan carries the
on-device step loop (`loop_modes=1` when the grid fits one wave); C-2
validates `L1_loop` against the other modes.

MX-1 measured every cell row-major and let the solver choose a GEMV variant
for small-batch decode. MX-2 runs fragment-packed ("tiled") weights with GEMV
kept out of the domain; the protocol is otherwise identical, so the cells
compare directly. Baselines were not re-run (versions unchanged), so the vLLM
column is the MX-1 measurement in both ratios. Per-cell rows are in
[`MX1_gap_c550.csv`](MX1_gap_c550.csv) and `runs/mx2/mx1_vs_mx2.csv`; the
implementation each cell selected is in `runs/mx2/selected_impl.csv`
(**all 39 solved plans are tiled with no GEMV variant**).

| Qwen3-0.6B | B1,2,4,8,16 | 6.01-8.40 → 5.75-7.56 (-28%-+5%) | 11-85 → 10-73 | 1.75x-2.61x → 1.75x-1.87x | tiled |

**18 cells, median TPOT −16.0%** (range −35.8% to +5.0%) and **median TTFT
−16.0%** (−29.2% to −12.7%, improved in every cell). Against vLLM the ratio
falls from MX-1's 1.75–2.61x to **1.24–1.95x**, and Llama-3.1-8B B16 — which
MX-1 could not solve — now measures 20.25 ms/token. Two controlled A/Bs
isolate the causes, both on qwen3_0_6b with the plan pinned by
`--evaluate-configs` so only one thing changes:

- **Layout** (B16, same 7 geometries): row 8.391 → tiled **7.351** ms/token,
  **−12.4%**; TTFT 92.5 → 81.2 ms. The row arm reproduces MX-1's 8.40 ms.
- **GEMV vs MMA** (B1/B2 decode): the solver priced GEMV as better, but
  forcing MMA on every class gave 8.026 → **5.823** (−27.4%) and 8.281 →
  **5.991** (−27.7%). GEMV also forfeits the tiled layout
  (`ServingGemvTaskBody` asserts `!Tiled`), so it is not the better
  implementation here and no per-class layout work was needed.

## 8. GPU usage (§0.3)

**Verified** from `runs/mx1/gpu_jobs.log`, appended by the guard wrapper on
every job: 925 guarded jobs, **16.67 GPU-hours** — GPU 7 (154 jobs, 10.28 h),
GPU 5 (111, 3.79 h), GPU 6 (647, 2.56 h), GPU 4 (13, 0.04 h). GPUs 0-3 never
touched, at most two cards at once, one job per card, all through `gpu_guard`.
GPU 6 carries a solve's short device queries (300 s cap each), GPU 7 the
baseline cells and GPU 5 the TileMega measurements.

Guard changes after it refused 21 valid cells (`091909e4d`, **verified**):
wait for a device to settle rather than refusing on the first busy sample;
widen the idle-power margin to the drift seen at 0% utilization (97 W nominal
vs 130 W sampled); size the hidden-memory budget per job, since the driver
attributes only part of a 31 GiB job's footprint.

## 9. Unfinished, with causes

1. ~~Decode plans with last-arriver do not build.~~ **Fixed**: codegen emitted
   `GemmGranularity`'s default tile instead of the selected one, illegal on
   xcore1000. A second instance of the same class of bug — the probe asserting
   the non-DM shape rule while a DM build runs `ServingDmGemm` — is also fixed;
   the rule now follows the body that will run (`GemmStageTaskBody.h`).
2. **Llama-3.2-3B does not solve, in either phase** (10/10 cells,
   **verified**). Its GQA ratio of 3 splits ISL 64 into 21-row chunks with a
   ragged tail, so a per-task count is 10 for three tiles and 5 for the last
   and has no scalar value; `FlowPreparation.cpp:139` needs one per stage, so
   `QuasiPolynomial::Eval` throws (decode: `max 80 != min 40`). Independent of
   `--attention-impl` and of last-arriver. Next: `evaluate_count` via
   `EvalPoints`, or price the padded tail the hardware executes anyway.
3. **MoE and DNN**, extra scope. The ResNet18 DM plan compiled. The
   Qwen3-MoE-24L decode solve, which MX-1 abandoned after 25.5 h without
   selecting, now **compiles**: the search stops at its budget (three
   `SEARCH_BUDGET` records), 267 candidates, ~92 min wall clock, and codegen
   reports `tasks=339 couplings=603 stages=219` (**verified**). Two blockers
   had to go first: the search had no stopping rule, and the CLI rejected
   `QPerKV > 4` although the only xcore1000 decode attention body supports
   `Q <= 8` and sizes its shared memory for it — which made the model
   uncompilable rather than merely unoptimized. It is not measured: the MoE
   needs a matching prefill plan and the MBU denominator must count routed
   experts, not all of them (MX-1's CSV reports 128–450% for it).
4. **Paged executor** not exercised (§5 permits it); Llama-3.1-8B B16 prefill
   hit `rc=124` at the 5 h cap after ~2600 evaluations, leaving 1 of 20 cells
   unmeasured — raise `CELL_TIMEOUT` or use one search pass.
5. **Variant multiplicity costs more than the layout saves** (**verified**):
   on qwen3_0_6b B4 decode, 1 variant + tiled is **5.167** ms against 6
   variants + tiled 6.31 and MX-1's 1 variant + row 6.01 — layout −14.0%,
   variant count +22.1%. The proposed mechanism is **refuted**: both plans
   report the same register ceiling (MTreg 248, STreg 108, no spill), so it is
   not a register budget; device code size differs 1.8 vs 3.3 MB, leaving
   instruction footprint as the surviving candidate. Next: price variant count
   in the cost model so the search stops trading a 22% regression for a 14%
   gain.
6. **`floor_ms` is a schedule bound, not a bandwidth one** (**verified**): it
   equals `binding_path_ns` exactly (5.059 ms on qwen3_0_6b B1 decode) out of
   `max(work_lb 2.349, queue_lb 4.199, binding_path 5.059)`. The pure DRAM
   floor is 0.781 ms and the semantic critical path 3.576 ms, so the solver
   rules out the region where vLLM measures 3.08 ms. Those two terms were not
   even dumped before (`bounds.tsv` only covers `outer_candidates`, which the
   serving search never fills); they are now in the metrics. Diagnosis only,
   per MX2-H — no cost-model change this round.
