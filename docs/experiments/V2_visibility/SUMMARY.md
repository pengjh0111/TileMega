# V2 —— 跨 block 数据可见性缺陷的定性与边界测定

> 环境：RTX 5090 (sm_120a, 170 SM)，driver 580.65.06，cuda-tile `af241704`，
> tileiras 13.3.1（Q9 另用 13.1 做对照），bytecode 13.3。
> 全部实验的 cubin、`.env.json`、MLIR、run.sh 都在本目录各子目录里。
> 统计纪律：除特别注明外，**每格 50 次全新进程**（V2-a′ 为 500 次）。

---

## 0. 一句话结论

**这个缺陷跟"跨 block 数据可见性"没有关系。** 它是 tileiras 把
"含 CTA 集体 barrier 的 `loop`" lower 成"逐线程谓词化回边"造成的
**barrier 配对错误**：自旋循环体内的 `BAR.SYNC 0x0` 与 `reduce` 跨 warp 归约级的
`BAR.SYNC 0x0` 是**同一个硬件 barrier**，落后的 warp 在自旋 barrier 上的到达
可以满足归约 barrier，于是 warp 0 在别人写完 partial 之前就把共享内存读走了。

判定失败与否的唯一开关是 **`reduce` 是否产生了共享内存跨 warp 归约级**。
数据是否跨 block 共享、事件是否分布、数据是不是 kernel 写的，**全部无关**。

## 1. 七个必答问题

### Q1. 数据 store / load 的指令在屏障的正确一侧吗？

✅ **在。§0.4(2) 的假设被直接观测证伪。**

producer 侧 `tile<1024xf32>` 的 `store_view_tko relaxed device` 展开成
**恰好 8 条 `STG.E.STRONG.GPU`**（0x0120–0x0190，步长 0x200），
**全部**位于 `BAR.SYNC`(0x01a0) / `MEMBAR.ALL.GPU`(0x01e0) / release 的
`ATOMG.E.EXCH.STRONG.GPU`(0x0210) **之前**，限定符完全一致，没有一条掉队。

consumer 侧展开成 **8 条 `LDG.E.STRONG.GPU`**（0x0390–0x0400），
**全部**位于 acquire 产生的 `CCTL.IVALL`(0x0370) **之后**。acquire load 被正确 CSE
掉（只剩 `CCTL.IVALL` 的副作用），这是合法优化。

而且这个"128 元素 = 一条 `STG.E` 的份额"的数值巧合在 V2-f 的尺寸扫描里直接崩掉：
tile 宽度 N=64 时丢的是 **32**，不是 128。丢失量恒等于**正确答案的一半**，
真正的量子是 **warp partial**（32 lane × 8 元素 = 256，N=64 时 = 32），不是访存指令。

细节见 [SASS_AUDIT.md](SASS_AUDIT.md) Q1–Q8。

### Q2. 事件与数据都分散时（V2-e），还有问题吗？——项目决策最关键的一问

❌ **有。而且 grid=8 就已经出错。**

事件完全分布式（每个 flag 一写一读、128B padding 避免伪共享）＋ 数据完全独占
（每个 chunk 一写一读）的**串行任务图链条**：

```
grid    failed/50
8       11/50
30      25/50
80      50/50
120     50/50
170     50/50
340     50/50
```

这是用户在任务书里预期的"极有价值的负面信息"：**per-tile 事件张量 + 独占数据
并不能规避这个缺陷。** V1 的那个结论（虽然当时是「下早了」）方向上是对的，
只是理由完全不对。

⚠️ **我第一版的 V2-e 得出了相反的结论（300/300 全过），那批数据我自己作废了。**
原因是我让每个 block 先写完 1024 个 float 再去自旋，等它走到自旋点时上游 flag
早已翻转，**没有任何 block 真的自旋过**——测的是"没有真自旋时安不安全"。
把生产/消费顺序对调成严格串行链条后，才得到上表。详见 [V2_e/result.md](V2_e/result.md)。

### Q3. V1-a 是机制安全还是时序侥幸？

✅ **机制安全——但 V1 对"为什么安全"的归因是错的。**

grid=340，**每格 500 次**，四种扰动：

```
plain / host delay 5000us / host delay 50us / non-blocking stream / no-spin
0/500      0/500              0/500            0/500                 0/500
                                                       合计 0/2500
```

V1 认为 V1-a 干净是因为"每个 block 读自己独占的 chunk"。真实原因是
**V1-a 根本没有 `reduce`**（`grep -c reduce v1_a.mlir` = 0，SASS 里 `STS=1 LDS=0`，
没有跨 warp 归约级）。V1-a 与 V1-b 之间**一次变了两个量**（数据共享性 + 有无 reduce），
V1 把功劳记在了错的那个上。

直接 A/B：保留 V1-a 的独占数据形态、**只加一个 `reduce`**（`v2_y_shared_excl`），
grid=340 → **50/50 失败**。独占数据没有救它。

### Q4. 失败与 tile 大小 / 多指令展开有关吗？

✅ **与 tile 大小有关，但不是通过"多指令展开"，而是通过"tile 是否宽到需要跨 warp 归约"。**

grid=340，数据一律由 **host 预填**，消费者 reduce 一个 `tile<Nxf32>`：

```
tileN  expect  failed/30   典型错值
32     32      0/30        —          单 warp，SHFL 就够，SASS 里没有 STS/LDS
64     64      30/30       32         = 正确答案的一半
128    128     30/30       64
256    256     30/30       128
512    512     30/30       256
1024   1024    30/30       512
```

N=32 时整个 tile 落在**单个 warp**内（32 lane × 1 元素），归约全靠 `SHFL.BFLY`，
SASS 里**没有 `STS`/`LDS`** → 永不出错。N≥64 一旦需要 `STS`/`BAR.SYNC`/`LDS`
把多个 warp 的 partial 拼起来 → 必错，且丢失量恒为正确答案的一半（= 2 个 warp 里丢 1 个）。

另外两个剥离对照（[V2_f/result.md](V2_f/result.md)）：

- `v2_f1`：自旋后只读 **1 个元素**、不 reduce → **0/50**
- `v2_f1024`：读满 `tile<1024xf32>`、逐元素写回、不 reduce → **0/50**

所以"访存指令条数多"本身完全无害。8 条 `LDG` 照样安全，只要不 reduce。

### Q5. 阈值跟 grid 走还是跟并发读者数走？

✅ **跟并发读者数走。V1 的"grid 80/120 尖锐阈值"不成立。**

grid **固定 340**，只改参与握手的消费者数 K：

```
K      failed/50
2      0/50
8      2/50
32     22/50
128    50/50
339    50/50
```

grid 一个字节都没变，失败率从 0% 单调升到 100%。而且**中间态很宽、是概率性的**，
不是 V1 描述的"80 全过、120 全错、无中间态"。

独立佐证：本轮用全新进程重扫 grid 得到 80→19/50、120→3/50、170→36/50、340→50/50，
**非单调**。V1 的"阈值"来自同进程内多次 rep 聚合，掩盖了"只有 rep 0 会错"——见 §2。

### Q6. 数据量的影响是单调的吗？

❌ **不单调，基本无关。**

grid 固定 170，载荷 P ∈ {1,4,16,64,256} 个 chunk：

```
P        1      4      16     64     256
failed  16/50  24/50  19/50  16/50  24/50
```

32%–48% 之间平坦。但**每一个亏损都是 256 的整数倍**（= 一个 warp partial）：

```
4096-1792=2304=9x256   16384-7936=8448=33x256   65536-59648=5888=23x256
262144-248832=13312=52x256   262144-256256=5888=23x256
```

载荷越大、循环里 reduce 次数越多，丢的 partial 个数越多，但每次都丢**整数个 partial**。

### Q7. 能否定性为 tileiras 缺陷？最小复现是什么？

✅ **能。** 见 [NVIDIA_ISSUE_DRAFT.md](NVIDIA_ISSUE_DRAFT.md)。

定性依据（每一条都可复现）：

1. 结构等价的 CUDA C++ 对照 `cuda_control.cu` 通过 —— 排除硬件/驱动/算法。
2. `v2_f_hostdata`：被归约的数据由 **host 在 launch 前写好**，kernel 里没有任何 block
   碰过它 —— **跨 block 可见性在物理上不可能是解释**，它照样 50/50 失败，
   错值签名与 `v1_min` 一模一样。
3. SASS 直接观测到成因：自旋 `loop` 的回边是逐线程谓词化的，而循环体里有一条
   CTA 集体 `BAR.SYNC 0x0`，与归约级用的是同一个 barrier。
4. 交替填充实验（§2）直接抓到"读到上一次 launch 的 partial"这一现行。

最小复现：`sass_audit/v1_min.mlir` + `v2_host.cpp`，grid=340，50 次，100% 复现。

## 2. 机理：直接抓到的现行

前面所有边界数据都只能说"某处丢了整数个 warp partial"。真正把机理钉死的是下面这个
**配对实验**（[mechanism_altfill.sh](mechanism_altfill.sh)，同一个 kernel、同一个 grid、
同一个 rep 数，**唯一差别是每次 rep 被归约的值变不变**）：

```
C) 常量填充（对照）—— 只有 rep 0 会错
  rep 0 expect=1024   12 bad :  512 x12
  (rep 1..7 全干净)

B) 交替填充 1.0 / 3.0 —— 每一个 rep 都错
  rep 0 expect=1024   17 bad :  512 x17
  rep 1 expect=3072   17 bad :  1536 x2   2048 x14  2560 x1
  rep 2 expect=1024   17 bad :  2048 x16  2560 x1
  rep 3 expect=3072   33 bad :  1536 x3   2048 x30
  rep 4 expect=1024   26 bad :  2048 x26
  rep 5 expect=3072   18 bad :  1536 x9   2048 x9
  rep 6 expect=1024   44 bad :  1536 x1   2048 x42  2560 x1
  rep 7 expect=3072   27 bad :  2048 x26  2560 x1
```

✅ **`rep 2 expect=1024` 却返回 `2048`。** 正确答案是 1024，返回值比正确答案**大一倍**。

这在任何"数据没到 / 读到 poison(−1.0) / 读到陈旧全局内存"的模型下都是**算术上不可能**的
——那些模型只能让结果**偏小**。2048 只有一个来源：

```
2048 = 2 x 256  +  2 x 768
       ^本轮正确的 partial   ^上一轮 (fill=3.0) 遗留在共享内存槽里的 partial
```

4 个 warp partial 槽里，有 2 个装的是**上一次 kernel launch 留下的值**。
rep 0 之所以在常量填充下也会错，是因为那时共享内存是冷的（读到 0），
`1024 - 2x256 = 512` —— 正是常量模式下唯一能看到的错值。

而常量填充时 rep 1..7 全干净，不是因为它们没出错，而是因为**上一轮的残留恰好等于
本轮的正确值**，错误被完美地掩盖了。这解释了 V1 的"阈值"为什么是假的：
V1 在同一个进程里 rep 聚合，看到的是"错误率随 grid 跳变"，实际是
"rep 0 的错误被后续 rep 稀释"。

对照组 D（`v1_min`，producer 写常量所以正确答案不随 host fill 变化）只有 rep 0 出错，
与模型一致。

### 与 SASS 的对应

```
/*0320*/ LDG.E.STRONG.GPU R3, ...        每个线程独立 load 同一个 flag
/*0330*/ BAR.SYNC.DEFER_BLOCKING 0x0 ;   <- CTA 集体 barrier，在自旋循环体内
/*0350*/ @P0 BRA 0x320 ;                 <- 逐线程谓词化回边，P0 非 CTA 一致
...
/*05b0*/ @!P0 STS                        各 warp 写自己的 partial
/*05c0*/ BAR.SYNC.DEFER_BLOCKING 0x0 ;   <- 同一个 barrier 0
/*05f0*/ @!P1 LDS                        warp 0 读回 partial
```

`/*05c0*/` 这条本应分隔"所有 warp 写完 partial"与"warp 0 读回"的 barrier，
可以被**还在 `/*0330*/` 自旋的落后 warp 的到达**所满足。

## 5. §3.5 的顺带核对：R2-D 的 blockDim=256

> 只报告，未改 R2-D 的文件。

✅ **已验证：driver 只接受 blockDim ∈ {1, REQNTID}，其余一律 `invalid argument`**
（`cuLaunchKernel` 和 `cuLaunchCooperativeKernel` 行为一致）。cuda-tile README 说的
"must be (1,1,1)" 不完整——REQNTID 也被接受。

✅ **已验证：cooperative 准入用的是 REQNTID，即使 blockDim=1。**
实测一个 REQNTID=128 的 kernel 以 blockDim=1 启动，最大 grid = **2040** = occ(128)×170。

R2-D 的 kernel REQNTID=256、REG=228 → 每 SM 只放得下 1 个 CTA → 上限 170。
**所以 R2-D 报的 170 是对的，但对得很偶然**：blockDim=256 恰好等于那个 kernel 的 REQNTID
才没被拒。V0 rebaseline 之后 REQNTID 变成 128，同样的 blockDim=256 会被**直接拒绝**，
而正确的上限是 **2040**，不是 170。

⚠️ **170 这个数字不能作为通用结论往后传。**

## 6. 对项目的直接影响

1. **不要再把工程量投在"重新编排事件/数据布局"上。** V2-e 证明真实任务图形态
   （分布式事件 + 独占数据）在 grid=8 就失败。布局不是杠杆。
2. **规避手段是明确的**：只要 megakernel 的 tile 任务体内**不出现需要共享内存跨 warp 级的
   `reduce`**，当前工具链就是干净的（V1-a 0/2500，`v2_f1` / `v2_f1024` 0/50，N=32 0/30）。
   这对 elementwise / 逐 tile 搬运类算子够用，对 GEMM/softmax/归约类算子**不够用**。
3. **这是 tileiras 的缺陷，应当上报。** 草稿已备。在修复之前，
   "spin-wait + 跨 warp 归约" 这个组合在 Tile IR 上不可用。
4. **`weak` 的用法要改**（规范 §7.2），但那是**规范符合性**问题，
   与本缺陷无关（V2-d′ 实测贡献 0%）。两件事不要混着报。
