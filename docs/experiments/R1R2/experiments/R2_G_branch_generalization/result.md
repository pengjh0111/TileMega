# R2-G: 分支数增多时 MAX-not-SUM 规律是否成立（N=2/3/5/8 泛化测试）

## 结论速览

**✅ 已验证（部分泛化，见下方限制说明）：MAX-not-SUM 规律在 N=3/5/8 分支下依然成立，
没有观察到向 SUM 退化的迹象。** 寄存器数在 N=2/3/5/8 全部锁死在硬件上限附近的 255
（因为工作负载调色板里始终包含 E2 的 128x128 `mmaf` 分支，其单独编译就已把 REG 顶到 255），
共享内存字节数从 N=2 的 99392 缓慢单调增至 N=8 的 99600（+208 字节，约 +0.2%），
远不是"分支数量线性叠加"的规模（若是真正的 SUM，N=8 相对 N=2 应多出至少 5 个额外分支的
独立 SHARED 开销，量级应为数千至上万字节，而不是 208 字节）。

## 方法

`gen_branches.py` 生成 N 路嵌套 `if/else` dispatch kernel（cuda_tile 只有二元 `if`，
N 路 dispatch 编译成 N-1 层嵌套二元 if/else 链）。分支工作负载从固定 4 元素调色板循环取用
（复用/扩展自 E2 的模式）：`mm128`（128x128 `mmaf`，即 E2 分支A原型，单独编译 REG=255）、
`red256`（256 元素 `reduce` 求和）、`mm64`（64x64 `mmaf`）、`red1024`（1024 元素 `reduce` 求和），
保证 N=8 时调色板刚好用满一轮，N=3/5 是调色板的前缀截取，具备可比性。

每个 N 值走完整链路：`cuda-tile-opt`（verify）→ `cuda-tile-translate`（tilebc）→
`tileiras --gpu-name sm_120`（cubin）→ `cuobjdump --dump-resource-usage`（读取 ELF 静态资源占用）。

N=2 基线数字取自 round 1 `E2_heterogeneous_tiles/result.md` §5 的 `cuobjdump --dump-resource-usage`
数据（`resource_usage.log`），而不是该实验里的 `cuFuncGetAttribute` 数字——两套工具口径不同
（driver 运行时 shared memory carveout vs ELF 静态段大小），round 1 E2 已经确认两者"数值有出入
但结论方向一致"，本实验为保证 N=2/3/5/8 四点严格可比，统一全部使用 `cuobjdump
--dump-resource-usage` 这一种口径重新读取（避免重复 round 1 E5 里"对照组选错"那类错误）。

## 结果

| N | verify | translate | tileiras | REG | STACK | SHARED | 备注 |
|---|---|---|---|---|---|---|---|
| 2（round 1 E2, `heterogeneous_dispatch`） | exit=0 | exit=0 | exit=0 | 255 | 8984 | 99392 | 调色板前 2 项：mm128, red256 |
| 3 | exit=0 | exit=0 | exit=0 | 255 | 8984 | 99416 | +mm64 |
| 5 | exit=0 | exit=0 | exit=0 | 255 | 8984 | 99448 | +red1024, +mm128(重复) |
| 8 | exit=0 | exit=0 | exit=0 | 255 | 8984 | 99600 | 调色板循环两轮 |

原始命令输出（N=8 示例）：
```
$ cuobjdump --dump-resource-usage branch_dispatch_n8.cubin
Function branch_dispatch_n8:
 REG:255 STACK:8984 SHARED:99600 LOCAL:0 CONSTANT[0]:928 ...
```

## 分析

1. **REG 保持恒定 255**（✅ 已验证，N=2/3/5/8 完全一致）：由于调色板里含有 `mm128`
   （E2 分支A原型，单独编译已是 REG=255，即硬件寄存器分配的实际上限附近），只要 N≥2 且
   调色板包含这一分支，REG 就已经被这一个分支锁死在 255，继续增加分支数（用其他更"便宜"的
   workload）不会也不可能再让 REG 继续升高（255 已经是 round 1 E2 §5 记录的、这块硬件/
   工具链组合下寄存器分配能达到的实际上限附近）。这是 MAX-not-SUM 规律里"寄存器"这一维度
   最强的正面证据——**如果是 SUM，N=8 时 8 个分支各自的寄存器需求相加必定远超硬件寄存器文件
   总容量，tileiras/ptxas 会报错或做寄存器溢出到 local memory（LOCAL 不再是 0），而实测
   LOCAL 全部保持 0，REG 全部保持 255，没有任何溢出迹象**。
2. **STACK 完全恒定 8984**（✅ 已验证，N=2/3/5/8 无一例外）：栈帧大小同样只取决于调色板里
   最贵分支（`mm128`）的需求，与分支数量无关，是另一条独立的 MAX-not-SUM 证据。
3. **SHARED 缓慢单调上升但远非线性叠加**（✅ 已验证 SHARED 确实存在一个小幅、随 N 增长的
   增量，⚠️ documented-but-unverified 精确归因）：N=2→N=8，SHARED 从 99392 增至 99600，
   增量 208 字节，平均每增加一个分支约 +35 字节。对照：`red256`/`red1024`/`mm64` 单独编译的
   共享内存需求量级（round 1 E2 未单独测过这三者，但 `mm128` 单独编译已是 100400，`red256`
   单独编译仅 16——若真是 SUM，每加一个分支应贡献至少几十到上百字节甚至更多）。**208 字节
   这个总增量数量级更接近"每个分支各自的 if/else 控制流跳转表/少量元数据开销"的线性叠加，
   而不是"每个分支各自完整 tile 缓冲区"的线性叠加**——换言之，MAX-not-SUM 规律对"计算所需的
   主要 tile 数据缓冲区"依然成立，但**分支调度本身（嵌套 if/else 的 CFG 结构）会引入一个很小的、
   随分支数增长的固定开销**，这一点 round 1 E2（只测了 N=2）没有观察到，是本实验的新发现。
   未定点验证的部分：没有做"单独编译 N=8 但去掉所有 tile 计算、只留空 if/else 骨架"的对照组
   来精确分离"CFG 调度开销"和"是否有极小一部分 workload 相关 SHARED 也在做微弱累加"这两种解释，
   标记为 ⚠️。
4. **循环嵌套 if-in-loop（3 层嵌套）测试**：❌ 未完成，本轮时间预算内未实施。
5. **loop-carried 值跨分支是否会使 MAX 退化为 SUM**：❌ 未完成，本轮完全未测试这一子问题
   （需要构造一个 `loop`/`for` 内部包含 `if` 分支、且分支产出的值作为 `iter_values` 带入下一次
   迭代的 kernel，这类 kernel 目前在 round 1/2 全部产出物中都不存在，需要新写）。
6. **tileiras 编译耗时随 N 增长明显上升**（⚠️ documented-but-unverified，附带发现）：N=3 编译
   在数十秒内完成，N=5 编译耗时超过 2 分钟（触发了 Bash 工具默认超时，需改用后台 `nohup timeout
   600` 才完成），N=8 的编译同样在后台运行了较长时间（具体秒数未精确计时，只确认在数分钟量级内
   完成）。这与本轮任务里 R2-H（编译期延迟测量）相关，但本实验没有为 R2-H 做严谨的计时测量
   （没有用 `time` 精确记录三次编译的墙钟时间），这里只作为定性观察记录，不作为 R2-H 的正式数据。

## 结论对 megakernel 可行性的意义

1. **✅ E2 的核心正面结论（"多路异构分支合并不会导致资源开销随分支数线性叠加"）在 N 扩大到
   3/5/8 后依然成立**，且在寄存器和栈帧这两个最容易"爆炸"的维度上是完全恒定不变的 MAX，
   没有观察到任何退化迹象——这进一步巩固了 E2 对 megakernel 任务图节点异构性可行性的正面证据，
   把验证范围从"只测过 2 个分支"扩大到"测过 8 个分支"。
2. **⚠️ 新发现的小幅 SHARED 随 N 增长的开销**（+208 字节 / 6 个新增分支，N=2→N=8）需要在
   megakernel 任务图节点数量非常多（例如设计目标里提到的"17 种算子"）时留意——虽然量级很小、
   目前看不构成实际风险，但没有做外推验证"分支数继续增长到 17+ 时这个开销是否依然是线性小量，
   还是会在某个规模后开始加速增长"，这是一个诚实标注的开放问题。
3. loop-carried 值跨分支、3 层嵌套 if-in-loop 这两个更接近真实 megakernel 任务图复杂度的场景
   完全未测试，round 1/2 报告都不能对这两点做出任何断言（❌ 未验证，非 ✅ 也非 ❌ 的"已证伪"，
   而是彻底的知识空白，需要后续轮次补充）。
