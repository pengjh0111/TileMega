Deviations, all **verified** unless noted:

1. **Last-arriver handoff is off** (`--nonpaged-la 0`) for both phases, which
   is what the MX-C/MX-T cells that validated this port ran. On prefill a plan
   carrying it is refused at load (`ServingRuntime.cuh`: it needs
   `TILEMEGA_SERVING_SEQ==1`). On decode the candidate it selects is not
   buildable — see §9.1.
2. **Row-major non-paged weights** (`--nonpaged-weight-layout row`) for both
   phases. `ServingGemvTaskBody`'s xcore1000 specialisation rejects the tiled
   layout outright (`static_assert(!Tiled)`), decode at M≤4 dispatches to it,
   and a cell's two plans share one process, so both phases must agree.
3. **torch.compile MoE experts run eager.** This MetaX torch has no
   `torch._grouped_mm`; the harness probes for it, falls back, and records
   `grouped_mm_error` in the measurement (commit `217024176`).
4. **Baselines are one round for the MoE cell, two for the dense cells.** The
   user reduced the three-round protocol to one; rounds 1–2 were already
   complete for the dense models and are both reported.
5. `counted_dependency_cg` fails at `test/unit/counted_dependency_cg_test.cpp:105`.
   **Inferred pre-existing**: the test and `BuildDependencyTableLinear` last
   changed before the baseline, and no commit on this branch touches the
   host-side lowering it asserts on. Verifying would need a build at
   `243fe9d06`.

## 8. GPU usage (§0.3)

**Verified** from `runs/mx1/gpu_jobs.log`, which the guard wrapper appends to
on every job: 602 guarded jobs, **9.83 GPU-hours**, on GPU 7 (154 jobs,
7.77 h), GPU 6 (441 jobs, 1.94 h) and GPU 5 (7 jobs, 0.12 h). GPUs 0–3 were
never touched; at most two cards were in use at once; every job ran through
`gpu_guard` with one job per card. GPU 6 carries the many short device queries
a solve makes (300 s cap each); GPU 7 carries the timed benchmark cells.

Guard changes made after it refused 21 valid cells (commit `091909e4d`,
**verified**): wait for a device to settle instead of refusing the moment it
samples busy; widen the idle-power margin to the observed drift at 0%
utilization (97 W nominal against 130 W sampled); size the hidden-memory
budget per job, because the driver attributes only part of a 31 GiB job's own
footprint and the MoE baseline flagged itself as a second tenant.

## 9. Unfinished, with causes

1. **Decode plans with last-arriver do not build.** `qwen3_0_6b` B1/B2/B4
   decode logged `NONPAGED_LAST_ARRIVER selected=112`, then `cucc` failed on
   `static_assert(ServingBF16ShapeLegal)` for
   `ServingGemmConfig<Xcore1000,16,32,16,3>` — tile_k 16 with 3 stages, where
   the serving GEMM body allows k ∈ {64,128}
   (`include/tilemega/Solver/BackendCostQuery.h:135`). `PruneServingR1`
   (`include/tilemega/Solver/ServingPruning.h:29`) checks exactly that
   predicate, so the last-arriver path reaches codegen without it. Next step:
   apply R-1 to the handoff candidate before it is selected. Worked around by
   deviation §3.1.
2. **Llama-3.2-3B prefill does not solve.** 24 q over 8 kv heads is a GQA
   ratio of 3, which splits ISL 64 into 21-row chunks with a ragged tail, so a
   per-task count is 10 for three tiles and 5 for the last:
   `{ [m,g] -> ((10 - 5*floor((5m)/16)) + 5*floor((4 + 5m)/16)) : … 0 <= g <= 7 }`.
   `FlowPreparation.cpp:139` needs one scalar per stage and
   `QuasiPolynomial::Eval` throws. Not attention-impl dependent; **decode is
   unaffected** (the same quantity evaluates to a constant). Next step: either
   teach `evaluate_count` to use `EvalPoints` per position, or keep the count
   uniform by pricing the padded tail the hardware actually executes.
   Filtering the query-row tile list for divisibility does *not* help —
   `group*serving_seq` is 192, which 16, 32 and 64 all divide.
3. **MoE and DNN** are outside MX-1 and were run as extra scope: the
   ResNet18 DM plan compiled (`tasks=24 couplings=31`, **verified**); the
   Qwen3-MoE-24L decode solve was still searching when this was written.
4. **Paged executor** not exercised; §5 of the spec permits deferring it.
