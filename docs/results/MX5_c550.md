Spec file locations: `/root/Prompt/TileMega_MX5_prompt.md:270` (fixed
`Body::Prefetched` return type), `:272` (`kLoads` constexpr), `:284`
(geometry/resource-dependent P_w), `:403` (six-coordinate instance sharing),

The formula admits different P_w for the same six coordinates. A CPU
reproduction is in `test/unit/mx/decode_geometry_v2.cpp:67`: Llama-3.2-1B O
(N=2048,K=2048) and down (N=2048,K=8192), B1, TN16/WN1/D1, residual, no norm,
TileRange, G104. Conditional on R_next=156, the prescribed widths are 8/16,
and their per-lane weight load counts are 8/16. **156 is a permitted example,
not a measured v2 resource value.** Coverage, owner and contributor-count
properties of both partition types passed on CPU (verified).

A single fixed `Body::Prefetched::kLoads` cannot express both widths under
the literal shared-instance contract. Following the user's authorization,
derived P_w participates in implementation specialization/instance sharing.
The six searched coordinates, prescribed width formula, compile-time kLoads,
runtime bench N/K/B and shared body source are retained. P_w is not searched.
The current bench uses a build-time P_w macro; measuring R_next at P_w=0 and
dispatching derived specializations in bench/program remain to be implemented. Compared with spec §4.12, equal six-coordinate tuples may therefore
have separate instances when their prescribed P_w differs. Stage B continues.

## Open resource defects and recorded differences

`MX5_body_resources_c550.csv` labels unit builds separately from stage-bench builds;
it contains no model resource claim. Rows are append-only. Compiler stdout and
stderr sometimes interleave a warning summary inside a mangled kernel name;
the parser recovers the name while preserving the raw log.

1. The tested 576-thread kernels can spill at MTreg 168, below the spec's 227
   aggregate bound. A matching 512-thread deep-prefetch diagnostic reports
   MTreg 178, local bytes 0, occupancy 1. Per-PEU allocation is a possible
   explanation (inferred), not a measured hardware limit. The closest resource
   rule is intended to consider persistent stack frames when applying the
   512-thread exception. This is an interpretation authorized by the user,
   not implemented plan rebuilding; final plans must still have zero stack.
2. At P_w=D, 512-thread unit builds still fail resources in **54/434 GEMM**
   kernels (TN128/D2--3 or TN64/D4) and **2/30 head** kernels (TN128).
   Max frames are 644/252 B. These remain defects at
   `DecodeGemmV2.h:226` (ring) and `DecodeHeadV2.h:50` (tile loop).
   Attempts to merge payload storage did not resolve them; failed artifacts
   are retained. **G-B is not passed; these instances are not enabled.**
3. The formal residual domain TN128/WN4/B16 needs up to two 16 B vectors per
   thread, versus §4.8's stated maximum one. Both are loaded early; all such
   unit cases pass. Covered dense residual shapes cannot legally select that
   tuple under WN <= ceil(T/G); their mapping needs at most one vector.

## Measurements contradicting the spec's inferences

No measured contradiction to the appendix's model-performance predictions is
